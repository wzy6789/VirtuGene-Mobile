## 1. 闭环现在通了

```
世界剧场：一起演一场戏（1 轮 1 次调用）
   → 结束结算（1 次调用）→ 写进世界层：stage 事件 / 共同记忆 / 关系变化（带原因）/ 未完成事件 / 参与者认知
        ↓（Phase 3b：每次发消息前的纯本地召回）
   私聊 systemPrompt 新增区块「[你们一起经历过的事（世界舞台）]」
        ↓
   角色可以像回忆一件真事那样提起它（"那天在便利店…"）
        ↓
   Message.contextTrace.sceneIds 如实记录 →「记忆依据」面板出现「你们一起演过的戏」
```

**验收里是真的跑完整条链路的**：用真实 `scene-runtime` 演完一场戏（推演 + 结算），
再在真实 `ChatWindow` 里发消息，然后断言**真实的 systemPrompt** 里出现了这场戏。
没有任何一环是用假数据糊过去的。

## 2. 三道闸门（与共同记忆完全同构，因此行为可预期）

| # | 闸门 | 实现 | 如果缺了会怎样 |
|---|---|---|---|
| 1 | **参与过** | `WorldScene.characterIds` 必须包含该角色（且只召回 `status === 'finished'` 的戏） | 没上场的角色会"记得"自己没经历的事；还在演的戏会被当成"我们经历过" |

| 3 | **可见性** | `lib/world/visibility.ts` 的统一闸门（与结算写入的 `selected + visibleTo=参与者` 对齐） | 防御性：将来有人单独改了事件可见性也不会泄漏 |

召回上限 **2 场**（戏是长篇；再多会把上下文挤满），按 `finishedAt` 取最近的。

## 6. 一个设计事实（验收过程中确认的口径，值得记录）

验收 D 组一开始我写错了期望：我以为"这场戏留下的共同记忆"会通过 2b-3 的共同记忆区块**再注入一次**。
实际不会，**这是对的**：

- 结算时那条共同记忆是挂在 **`stage` 事件**上的（`memoryIds`）；
- 2b-3 的共同记忆召回**只认 `shared_memory` 类型的事件**（当时的口径就是"关系变化与场景后果不在那里重复注入"）；
- 所以同一次经历**只由舞台区块呈现一次**，而舞台区块给的是"标题 + 地点 + 时间 + 发生了什么"，
  信息量严格多于那一行记忆标题。

我把这条口径写进了验收（断言记忆标题出现 **0 次**、摘要恰好 1 次），并在代码注释里说明原因——
避免以后有人"顺手"把 stage 事件也接进共同记忆召回，从而让同一件事在 prompt 里出现两遍。

## 8. 已知限制

| # | 项 | 说明 |
|---|---|---|
| L1 | 只召回 **2 场**、只给"标题 + 地点 + 时间 + 一句摘要" | 有意为之：戏的正文太长，逐字注入会挤爆上下文。若你希望角色能引用更多细节，需要做"场景摘要分级"（另一次产品裁定） |
| L2 | 没有"关键词相关性"排序 | 与共同记忆一致：按结束时间取最近 2 场。场次多了以后，可能需要按当前话题挑（§39 那套打分已有实现，可复用） |
| L3 | 没有"冷却"机制 | 与 2b-3 的 L4 同一个问题：提示词里要求"不要每次都提"，但只是软约束，需真机观察 |
| L4 | 舞台里"正在发生"的部分不会进私聊 | 只召回已结束的戏（正在演的内容属于舞台，不该在私聊被当成回忆） |
| L5 | 群聊未接入 | 群聊上下文仍是 4.x 的；场景召回目前只接私聊 |
| L6 | baseline 之后 11 个阶段仍未提交 git | **越拖越贵**，强烈建议尽快落一次提交 |
