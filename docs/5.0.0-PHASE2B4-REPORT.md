## 1. 一句话

日记从"要么全给所有角色看（旧全局开关），要么谁都不能看"变成了**逐条、可撤回的授权**：
**仅自己（默认）/ 告诉某角色 / 加入共同世界**；并且**旧的全局绕过入口已被彻底删除**。

```
我的生活（日记）
 ├─ 仅自己        → 不写世界事件、不给任何角色认知           ← 默认
 ├─ 告诉某角色    → 只给该角色"认知 + 可提起"，**不写世界事件**（"只告诉你一个人"不留世界年表痕迹）
 └─ 加入共同世界  → 写 reality 世界事件（你的生活）+ 按参与者建立认知
                        ↓（每次发送前本地判断）
        listVisibleFor（逐条可见性，private 永不返回）
      + listMentionableDiaryIds（该角色确实知道且可提起）
                        ↓
        systemPrompt 区块「[用户主动让你知道的日记]」
                        ↓
  撤回（改回仅自己 / 换授权对象 / 删除日记）→ **下一次发送立即不再注入**
```

## 3. 数据与写入规格

| 可见性 | 世界事件 | 认知（谁能提起） |
|---|---|---|
| `private`（默认） | 不写 | 无 |
| `selected`（告诉某角色） | **不写**（"只告诉你一个人"不进世界年表） | **只**给 `visibleTo` 的角色：`full` + `canMention` |
| `world`（加入共同世界） | 写一条 `reality` 事件（`visibility:'world'`，参与者 = 你 + 该条日记关联的角色） | 按**参与者**建立（关联角色获得） |

**认知锚点**：日记的授权认知挂在 `diary:<diaryId>` 上（`CharacterKnowledge.eventId` 在这里当"认知锚点"用）。
理由：`selected` 按你的口径**不写世界事件**，而认知必须有个可挂载的锚点；
用同一个锚点表述"谁能提起这条日记"，判断口径只有一处，也不会与普通世界事件 id 撞名。
（若你更希望"告诉某角色也写一条 `selected` 世界事件"，我可以改成那种形态——这是一种取舍，不是技术限制。）

**撤回与清理**（都不留孤儿）：
- 改回 private / 换授权对象 ⇒ 删掉旧锚点上的认知行（`knowledgeRepo.removeForEvent`）。
- 降级（world → private/selected）⇒ 连同 `reality` 世界事件一起移除，`Diary.worldEventId` 字段**真的删掉**。
- 进回收站（软删除）⇒ 不注入（`listVisibleFor` 本来就排除 `deletedAt`），恢复后照旧生效。
- 彻底删除（回收站清空 / 7 天自动清理）⇒ 收回认知 + 移除世界事件。
- 角色被删除 ⇒ 从 `visibleTo` 摘掉该角色（其他人保留）；一个都不剩时自动回到 private；认知随角色删除。

## 7. 过程中的两个发现（都是测试先暴露出来的，如实说明）

1. **验收 I 组一开始"失败"，其实是测试接错了**：我把 `diary` 当**快照**传给控件，控件的文案自然不会更新。
   真实页面里 `diary` 是父组件 state（`DiaryChatPage` 用 `onChange` setState 回去），
   所以验收改成**给它一个有状态的父层**（`SharingHarness`）后再断言——这样"点完角色文案就变"才真的被验证。
2. **"全程零网络"这条断言被 4.x 的既有后台行为污染**：用户消息累计到一定条数时，
   4.x 会做一次上下文整合（`webApi.context.settle` → `consolidateContext`），它走自己的 `fetch`，
   在本阶段的验收里被记到了。我没有把它当成"我的成本"，也没有偷偷放宽断言，而是改成**按调用栈归因**：
   - 断言"日记闸门本身 0 网络"（直接量）
   - 断言"没有一次请求来自本阶段新增的代码路径（diary/recall/visibility）"
   - 断言"出现的请求全部来自 `consolidateContext` / `assignVoice` 这类 4.x 既有路径"
   （顺带说明：这条后台整合在真实设备上是**真实联网**的，属 4.x 既有设计，不在本阶段范围内。）

## 10. 审核修复：P1（情绪泄露）与 P2（区块重复注入）

你指出的两点都成立，都是**我的实现缺陷**，也都已在同一阶段内修好并补上真实 `ChatWindow` 提示词回归。

### P1 — 私密日记的**情绪**仍泄露给角色（`ChatWindow.tsx` 心情联动）

**问题**：内容区块已经过"逐条可见性 + 认知"两道闸门，但**日记心情联动**读的是
`diaryRepo.getByDate(userId, today)`——**今天全部日记**。于是：
一篇 `private` 的日记，内容不会被注入，**但"今天心情低落/不错"照样被告诉每一个角色**，
角色的语气会跟着变。用户能感觉到"它知道我写了什么"，而这条日记其实谁都没授权。

**修复**：心情联动与内容**共用同一个闸门**——只看"今天 **且** 这个角色被允许知道且确实知道"的日记：

```ts
const allowed = visible.filter((d) => mentionable.has(d.id));   // 可见性 + 认知
knownDiaries = allowed.slice(0, 3);
diaryShareContext = buildDiaryContext(knownDiaries);
const today = allowed.filter((d) => d.date === todayStr());      // ← 心情只看这一批
if (today.length > 0) { /* 低落 / 不错 */ }
```

顺带明确了一个语义边界：**心情联动只认"今天"的日记**（旧的往日日记内容可以进上下文，但不会影响语气）。

### P2 — 授权日记被重复注入提示词（`ChatWindow.tsx` 区块列表）

**问题**：`{ key: 'diary', text: diaryShareContext, priority: 70 }` 在 sections 数组里**出现了两次**
（我前一版把 `diary-share` 换成 `diary` 时，没有删掉更早插入的那一条）。
结果是同一整段日记内容被塞进 Prompt **两遍**：浪费预算、模型看到重复信息，
而且验收里"区块存在"这类断言**照样通过**——这正是你从代码里读出来、我的测试没覆盖到的原因。

**修复（两层）**：
1. 删掉重复的那一条（现在 `diary` 只出现一次）。
2. **结构上防止再犯**：`compileChatContext` 现在对 sections **按 key 去重**——
   同一个 key 只注入一次，重复时保留优先级更高的那一条（优先级相同保留先出现的，可预测）。
   这样"不小心写两遍"不再会静默地变成双份 Prompt。
