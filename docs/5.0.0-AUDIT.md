## 0. 审计方法与结论摘要

### 0.1 方法
逐个子系统读取真实实现并记录 `文件:行号` 证据（不依赖记忆、不猜）；用 grep 枚举全部 LLM 调用点、全部 Repository 方法、全部数据表与索引、全部动画关键帧；核对依赖版本与各项上限常量。

### 0.2 三个最重要的结论（决定 5.0 工程量）

**结论一：5.0 的「单次 Scene Director 请求」在代码里已经有原型，必须复用而不是重写。**
`src/lib/ai/group-chat.ts:76` 的 `generateGroupTurn()` 已经实现了"**一次调用 → 多个角色发言 + 结构化解析 + jsonMode 失败自动降级重试**"（`jsonMode` 契约见 `group-chat.ts:94-99`，`maxTurns` 见 `:130`，`maxTokens: 1500` 见 `:177`，解析器 `parseTurns` 见 `:254`）。这正是 §56 要求的 Scene Director 形态。5.0 应当把它抽成通用的 `scene-director.ts`（或在其上加一层契约），而不是新写一套多角色编排。

**结论二：§10「未完成的故事」、§27「可解释关系」的地基已经存在，5.0 是"加一层解释"而不是"从零建表"。**
- 未完成事件：`continuityThreads`（Dexie v15）+ `src/db/continuity-repo.ts`（去重、8 件上限、`open/done/dropped/archived` 四态、`completeByTitle`）。§10 只需把它包装成有产品感的入口，并补 `sourceSceneId`。
- 人物共同事件：`sharedStoryEvents` + `src/db/shared-event-repo.ts`（成对读取、双向去重、`viewpoints` 分侧视角）。§27 的"共同事件 N 段"已经能算出来。

**结论三：5.0 真正必须"新建"的只有四件事**：世界层数据模型（WorldEvent / SharedMemory / CharacterKnowledge / Scene）、场景运行时（World Stage）、世界首页、以及把场景后果写回既有系统的管道。其余全部是**扩展**。

## 5. 聊天系统实现

**核心文件**：`components/chat/ChatWindow.tsx`（50.9 KB，1141 行，全应用最复杂的文件）

4. 发图：自动写一条"用户分享了一张照片"的记忆（带去重）
5. 主动回忆：25% 概率抽一条旧记忆注入
6. 时间/关系/生命轨迹/故事关系/未完成事件/人物共同事件/用户情绪/日记心情/日记共享/长会话摘要/认识天数/口头禅 → 全部经 `compileChatContext()` 编译
7. 温度：`0.6 + proactivity * 0.3`
8. 质量自检重试：`checkReplyQuality`（`lib/reply-quality.ts`）最多 1 次修正
9. 落库 + 分条节奏：`splitReplyParts` + `computeMessageDelays`（`lib/chat-pacing.ts`，首条 350–900ms / 后续 450–1100ms / 长句 ≤1800ms / 总 ≤3500ms，`prefers-reduced-motion` 压缩）
10. `contextTrace`：只记录**完整注入**的记忆/未完成事件/共同事件 id（`ChatWindow.tsx:675-690`）
11. 每 **5** 条用户消息触发一次 `emotion-store.settle()`（情绪 + 记忆 + 未完成事件，**单次 API 调用**）
12. 长会话滚动摘要 `maybeSummarize`（`SUMMARY_WINDOW=18`，累积 8 条重算）

```

   ↓ ipc.xxx(params)                       src/lib/ipc-client.ts（1 行：window.virtugene ?? webApi）
Electron: preload window.virtugene  |  手机/浏览器: src/lib/web-api.ts (299 行)
   ↓

   ↓

   ↓  HTTP
DeepSeek / 千问 / MiMo / FLUX(图像) / Edge-TTS / MiMo-TTS / 云端 ASR / DuckDuckGo
```

**模型注册表**（`llm.ts:31-45`）：`deepseek`(api.deepseek.com/v1) / `qwen`(dashscope compatible-mode) / `mimo`(api.xiaomimimo.com/v1)；5 个模型：`deepseek-v4-flash`(默认, 视觉?) / `deepseek-v4-pro` / `deepseek-v4-flash-vision-exp`(vision) / `qwen3.7-plus` / `mimo-v2.5`。
**选择优先级**（`llm.ts:58-73` `resolveModel`）：会话锁定 > 角色指定 > 全局默认 > `deepseek-v4-flash`。
**参数策略**：DeepSeek 思考模式按轮次（文字 enabled / 视觉与结构化 disabled），MiMo 强制 disabled，Qwen 传 temperature；结构化场景用 `response_format: json_object`（`llm.ts:127`）；`max_tokens` 默认 1000。

## 18. 迁移风险（按严重度）

**R1（最高）· 日记隐私的历史数据归属**
现状是"一个全局开关控制**全部**角色读取**全部**日记"。§24 要求逐条可见性。升级时**不能**把"开关曾打开"当作授权（那等于把用户从没打算分享的内容一次性分发给所有角色）。
→ 策略：v16 升级时**一律**把既有日记置为 `PRIVATE`；把旧开关值迁移为"默认可见性偏好"（仅影响**新建**日记的默认选项），并在设置页给出一次性说明。宁可让用户重新授权一次，也不静默泄露。

**R2（最高）· Dexie v16 升级回调的安全边界**
升级回调在 IndexedDB 事务里执行，**不能 await 网络/长任务**，否则事务超时回滚。
→ 策略：回调内只做纯本地、分批（≤200 行/批）、幂等（按 `sourceType+sourceId` 判重）的派生写入；失败不影响旧表（派生数据缺失只是年表少几条，可后续补偿重建）。

**R3（高）· 派生事件重复写入**
`LifeEvent`/`SharedStoryEvent`/日记/场景都可能派生 `worldEvent`。若判重不严，会出现"同一件事在年表里出现两次"。
→ 策略：`worldEvents` 强制唯一键约定 `sourceType + sourceId`（迁移来源 = `migration:lifeEvent:<id>` 等），写入前查重；重复升级必须幂等（自检脚本要断言"升级两次行数相同"）。

**R4（高）· 不能清空/重置任何旧表**
v8 曾有清空先例。5.0 必须**只新增派生表与可选字段**，`characters/sessions/messages/memories/characterStates/diaries/groups` 零改写（除新增字段默认值）。
→ 策略：审计+自检断言"升级前后旧表行数与主键集合完全一致"。

**R5（中）· 多用户隔离**
`characterStates` 是复合主键，`groups/sharedStoryEvents/continuityThreads` 带 `userId`。新表**必须**统一带 `userId`（或从属角色推导），否则切换账号会串数据（历史遗留问题在 `sync.ts` 里已踩过：导入需重映射 `userId/createdBy`）。

**R6（中）· 命名冲突（5.0 术语 vs 现有代码）**
现有代码里已经有被占用的 "Scene/World" 词：
- `ImmersiveSceneCard.tsx` + CSS `.scene-card/.scene-grain/.scene-orb/.scene-thread/.scene-mini/.scene-prompt` + `@keyframes sceneFloat/sceneSweep`
- `LivingWorldHero.tsx` + `.vg-world-hero`
- `sharedStoryEvents`（人物共同事件）、`StoryTimeline`（共同时间线）、`LifeEvent`（生命轨迹）、`continuityThreads`（未完成事件）、`Diary`（手账）
→ 策略：新表/新模块统一用 `world*` 前缀且**不复用** `scene-*` CSS 命名空间（建议场景页用 `.stage-*`），并在 `docs/5.0.0-DATA-MODEL.md` 里固化术语表（WorldEvent / SharedMemory / CharacterKnowledge / WorldScene / LifeTrace）。

**R7（中）· 世界首页的查询成本**
首页要聚合"角色数 / 天数 / 共同记忆数 / 最近发生 / 未完成故事"，若逐角色 `getOrCreate` + 多表 N+1，会在低端机上卡首屏（现有 `ImmersiveSceneCard` 就曾因重复 `getOrCreate` 被要求优化）。
→ 策略：首页只读**已存在**的行（禁止 `getOrCreate` 副作用）+ 单次批量查询 + 派生数据在升级时预生成。

**R8（中）· 成本失控**
新增场景推演的 LLM 调用若按"每角色一次 + 旁白一次 + 判定一次"设计，成本会直接乘 3–5 倍（§56 明令禁止）。
→ 策略：**一次调用出多条**（复用 `group-chat` 契约）；仅在场景结束时做一次结算调用；退出场景不产生调用（§57）。

**R9（中）· 现有后台调度的相互叠加**
`dailyGreeting`(08/22 点)、群聊 `proactiveBackground`(10 分钟轮询 + 30 分钟冷却 + 4h banter) 已存在；世界层若再加定时器，需要统一到一个调度器与预算表。

**R10（低-中）· 已发布基线不一致**
线上 4.1.0 的 APK 与当前工作区不一致（工作区多两处改动）。开 5.0 前必须先落一次基线提交，否则回归测试无法判定"是不是 5.0 引入的"。

**R11（低）· 合规延续**
`UseTimeReminder`(2h)、`LegalNoticeModal`(隐私/条款)、AI 内容标识、18+ 确认、自伤安全引导（网关侧）必须继续生效；World Stage 生成的内容同样受"AI 生成内容标识"约束。

**R12（低）· 工程边界**
手机端仓库**自包含**（`lib/ai/*` 是桌面端纯函数的副本）。5.0 不得反向依赖 `F:\VirtuGene`；桌面端缺陷另行转达。

## 19. Phase 1 实现方案（Living World 数据基础）

**目标**：只做"存储 + 读取 + 迁移"，**零 UI、零新增 LLM 调用、零业务逻辑改动**。

### 19.1 数据模型（6 张新表 + 3 处字段扩展）

> 相对 §33 的建议清单做了合并，理由写在每张表后面（遵循"每增加一个模型都要说明为什么"）。

| 新表 | 关键字段 | 为什么需要 / 合并理由 |
|---|---|---|
| `worldEvents` | id, userId, **type**('reality'\|'shared_memory'\|'stage'\|'relationship'\|'knowledge'\|'life_trace'), title, summary, participants(string[]，含 'user'), timestamp, importance(0–1), **sourceType**, **sourceId**, visibility('private'\|'selected'\|'world'), resolved, relatedEventIds[], memoryIds[], tags[], emotion?, createdAt | **年表的唯一骨架**。"最近发生""未完成的故事""世界年表""Life Trace"全是它的视图；`LifeTrace` 不再单独建表（= type='life_trace' + 关联字段），避免两套时间源 |
| `worldScenes` | id, userId, title, place, timeLabel, mood, characterIds[], status('draft'\|'active'\|'paused'\|'finished'), theme?, actsDone[], **state**(结构化：sceneGoal/currentTension/activeSecrets/activeConflicts/pendingConsequences/participantGoals/participantStates), startedAt, finishedAt?, worldEventId? | §36 的 SceneState **内嵌**在主行（1:1、读写原子、免事务耦合）；`SceneParticipant` 用 `characterIds + state.participants` 表达，不单开表 |
| `worldSceneEntries` | id, sceneId, index, kind('narration'\|'dialogue'\|'choice'\|'user_input'\|'system'), speakerId?, content, meta?, createdAt | 场景逐条内容（§16 章节 UI + §58 分段渲染 + 断点续演）。与 `messages` 分开：结构不同（旁白/选择/幕次），且不能污染聊天记录与未读/摘要 |
| `characterKnowledge` | id, userId, **characterId**, **eventId**, knowledgeLevel('none'\|'hint'\|'partial'\|'full'), canMention, learnedAt, sourceCharacterId?, **isSecret**, secretOwnerId? | §15/§35/§62 的核心：**"发生过" ≠ "谁知道"**。`CharacterSecret` 合并进本表（isSecret + secretOwnerId），避免两张语义高度重叠的表 |
| `sharedMemories` | id, userId, title, summary, participants[], characterIds[], createdAt, sourceType, sourceId, importance, visibility, relatedCharacters[], relatedRelationships[], emotion?, tags[] | §26 的完整字段。**与 `memories` 严格分工**：`memories`=关于用户的事实（不动），`sharedMemories`=共同经历片段 |
| `relationshipEvents` | id, userId, **pairKey**(排序 a\|b，用户用 'user' 参与), subjects[2], facets{trust?,affinity?,dependency?,conflict?,familiarity?}, reasonText, sourceEventId?, sourceType, createdAt | §27/§28 的"可解释关系 + 关系史"；也是"某次场景让关系变了"的唯一记录点（现状只有当前值，没有原因） |

**字段扩展**：
- `Diary` += `visibility('private'\|'selected'\|'world')`（默认 `private`）、`visibleTo: string[]`、`worldEventId?`
- `ContinuityThread` += `sourceSceneId?`、`sourceWorldEventId?`
- `CharacterState` += `relationshipFacets?{trust,dependency,conflict,familiarity}`（**可选**，不改变现有 `affinity/mood` 语义与"不退阶"规则）

**Dexie**：`this.version(16).stores({...全部 11 张旧表原样..., worldEvents, worldScenes, worldSceneEntries, characterKnowledge, sharedMemories, relationshipEvents})` + `.upgrade(migrate4xTo5)`。

### 19.2 迁移（§50/§51/§52，零丢失）

| 来源 | 动作 | 幂等键 |
|---|---|---|
| `CharacterState.lifeEvents` | 每条派生 `worldEvent`（type 映射：interaction→stage? / memory→shared_memory / relationship→relationship / goal→stage）**原数据保留不动** | `migration:lifeEvent:<id>` |
| `sharedStoryEvents` | 每条派生 `worldEvent`(type='relationship', participants=pair) + `relationshipEvent`(reason=标题) | `migration:sharedEvent:<id>` |
| `continuityThreads` | 补 `sourceSceneId=undefined`；派生 `worldEvent`(type='stage', resolved = status!=='open') | `migration:thread:<id>` |
| `diaries` | **只加字段**：`visibility='private'`；**不派生世界事件**（§51 硬要求：旧日记不得被角色读取） | — |
| `memories` | **不迁移**（是"用户事实"，不属于共同经历） | — |
| `characters/sessions/messages/groups/characterStates` | **零改写**（除新增可选字段） | — |
| 旧全局开关 `diarySharedWithCharacters` | 迁移为"新建日记默认可见性偏好"，**不回填任何旧日记** | — |

### 19.3 验收（Phase 1 的自检，沿用本项目已有的可执行验证方式）

在真实 Chromium + 真实 Dexie 上跑断言脚本（我这次修 P1/P2 时用过同样的手法）：

1. **旧数据零丢失**：升级前后逐表对比行数 + 主键集合完全一致
2. **派生数量正确**：lifeEvents N 条 → worldEvents +N 条且 type 映射正确
3. **幂等**：连续升级两次，各表行数不变
4. **跨用户隔离**：两个 userId 的数据不互相派生/串读
5. **隐私默认**：所有既有 diary 升级后 `visibility==='private'`，且不存在任何指向旧日记的 `characterKnowledge`
6. **按角色/按对查询**：`characterKnowledge` by characterId、`relationshipEvents` by pairKey 返回正确
7. **`tsc --noEmit` 0 错误 + `vite build` 成功**（不改 UI，包体只增几个 KB）

### 19.4 需要你确认的 4 个取舍（Phase 1 开工前）

1. **`World` 要不要单独建表？** 我倾向**不建**：世界=该 userId 的全部数据，单行 `world` 表带来的收益（世界名/世界级设置）可以先用 `settings-store` 承担。若你希望"未来支持多个世界"，则现在建。
2. **`CharacterSecret` 独立表 vs 合并进 `characterKnowledge`（isSecret）？** 我倾向**合并**（少一张表、查询"TA 能不能提这件事"一次搞定）；但若"秘密"需要独立生命周期（被揭穿、被转告、被遗忘），独立表更清晰。
3. **场景内容用 `worldSceneEntries` 独立表 vs 塞进 `worldScenes.state`？** 我倾向**独立表**（长场景不会撑爆单行、可懒加载、可断点续演）；代价是多一次查询。
4. **场景是否复用 `sessions/messages`？** 我倾向**不复用**（场景有旁白/幕次/选择，复用会污染聊天列表、未读、摘要与导出）；但代价是要自己写渲染与分页。
