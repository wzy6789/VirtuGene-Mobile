# 私聊逐次用量统计修复

上一轮发现：空正文恢复的第一笔 usage 会丢失，质检重试只累计最终选中稿件。这使“为了人味多花了多少 tokens”的生产数据不可信。

## 已实现

- 直连 JSON、SSE 与网关在读取每次结果后上报 usage，空正文也在抛出恢复错误之前上报。请求中断或网络故障无法取得 usage 时记录未知；鉴权拒绝不伪造已消耗 tokens。
- 恢复过程中保留逐次事件，webApi 成功与失败都可返回元数据。回调仅含模型和计数，不含密钥、提示词或回复原文，且回调异常不会引发新的模型调用。
- 私聊在整个发送流程的 finally 中累计所有已观测事件，独立于选中稿件、是否保存成功或是否取消。回调和返回元数据选择一条来源，防止同一笔重复累计。
- 会话费用在 IndexedDB 事务内累加，检查账号及会话所有者。不同请求的元数据并发提交不会丢失；切换会话仍归原会话，切换账号的迟到数据不写入。
- 统计显示“次请求”，包括恢复与质检请求。未知用量、未识别的模型定价、旧桥接的不完整覆盖和无法追补的旧统计标为不完整，不宣称实际账单。
- OpenAI 兼容响应的计数缺字段、负数或空对象不再变成已知零。原生 Anthropic/Gemini 对应的基本计数也需要有效值，Anthropic 分帧输入与输出仍可接续。
- 真实测试工具现在同时读取应用落库 cost，后续实际对话能将应用统计和提供方用量对照。没有为统计增加模型调用。

## 验证

`node scripts/verify/chat-usage.mjs`：22 项，通过实际 transport 和 IndexedDB 验证空 JSON/SSE 恢复、计数有效性、未知请求、鉴权拒绝、回调异常、网关探测/空流、并发累加、账号隔离、旧统计保留、缓冲质检稿统计、真实私聊流式恢复落库及失败元数据。所有网络均为替身，零付费调用。

其中质检集成测试使用真实发送/质检/落库链路和一个不发布流式草稿的缓冲兼容适配器，确实产生两次 transport 调用并只保留较好的回复。这不冒充原生桌面实测；已显示 SSE 不做隐藏重写的规则仍由原有流式套件验证。

另外，547 项 chat-expression、56 项 chat-stream、363 项供应商协议检查通过，类型检查及生产构建通过。构建仍有既有动态/静态导入提示和约 514 kB 主包警告，不据此宣称性能达标。

## 实际边界

本仓库没有外部 Electron preload 的实现，不能宣称旧桌面桥接内部重试已全部接通。新的返回事件契约可接收逐次数据；只返回最终 usage 的旧桥接仍可显示已知部分，同时标为不完整。

这里记录的是私聊生成请求，不包括后台记忆提取、摘要、语音或主动/群聊的全部消耗，也不是账号总账。网络失败后的未知尝试是否实际产生收费无法由客户端证明；不会将未知字段当成零账单。价格是模型目录的估算，未精确还原缓存折扣；未知模型价格不冒充免费。

旧统计不清空，也不能凭空重建历史漏算。若本地数据库本身无法写入元数据，保留既有回复并记录不含原文的警告，不为记账失败重发模型；此时新统计仍可能缺失。没有做跨崩溃的消费日志或逐次 durable journal，因此不宣称进程突然退出时也绝不丢失统计。

## 对人味工作的影响

现在可以在正常读到元数据并完成落库的前提下对照“多次生成换来什么改进”。此次修复不改变人物措辞、生成模式或重试预算；说教、感受猜测与多角色长聊一致性仍需要继续优化和真实验证。
