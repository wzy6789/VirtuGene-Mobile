# 生活助理：给角色代发消息与带回回复

日期：2026-10-03。状态：单角色文字代发首版已实现，原方案保留为后续扩展规格。交付范围、实现取舍和本地验证见 `ASSISTANT-CHARACTER-MESSAGING-IMPLEMENTATION.md`；多角色、资料分享、定时及持续代聊尚未开放。

## 1. 产品目标与首版范围

用户留在助理聊天里，自然交代“给谁、说什么”，助理将经过授权的内容写入对应角色的真实私聊，调用该角色的既有回复能力，并在助理聊天里带回这一轮的真实回复。普通角色继续使用自己的设定、关系、记忆和模型；助理负责传话与办事反馈。

功能名称建议：**代发消息**；完成后主操作为 **查看回复**。它作为 5.3.x 助理的沟通能力扩展，沿用当前任务、补问、来源校验、收件箱和五种性格。

首版完成一个闭环：单个软件内普通角色、文字消息、即时单轮代发、真实角色回复、查看原聊天、暂停/取消、重开恢复和单独重试回复。对象限当前用户已添加的普通角色，包括由预设或公开角色克隆到自己账号的角色。助理自身、其他账号角色、角色库中尚未添加的模板、群聊均不进入首版收件人列表。

分阶段增加明确点选的多角色分别发送、资料分享和回复整理。定时发送、图片/语音、外部通讯平台和持续自动代聊另行设计。应用没有真实后台运行与调度时，只说明需要重新打开应用继续。

## 2. 依据当前实现的设计取舍

已核对的实现：

- `src/lib/secretary/agent.ts` 有规划、来源校验、补问、逐项执行、失败重试、回执与恢复，尚无角色消息工具。
- 普通私聊的上下文构建、流式请求、消息提交、记忆使用和关系更新主要位于 `src/components/chat/ChatWindow.tsx`，请求锁也保存在组件中。
- `src/store/chat-store.ts` 的 `shareDiaryToCharacter` 先选中目标角色，再写消息，通过 `pendingDiarySend` 交给 ChatWindow 生成回复。该状态没有持久任务凭证，而且切换角色会清除未读、可能创建开场白及触发声线处理。
- 角色列表按 `createdBy` 过滤当前用户已添加角色；私聊有分页消息接口，模型解析沿用会话配置、角色配置、全局配置的顺序。
- 助理工作资料与普通角色记忆目前分离；日记及衍生资料有解锁和来源保护，备份任务按数据恢复，不自动执行。

因此先提取一个与页面选择无关的角色聊天服务，让普通输入框、已有日记分享与助理代发复用同一条核心办理链路。助理页面订阅任务进展，用户点“查看聊天”才切换页面。角色未读、当前选中对象、声线和开场白由对应入口处理，不能成为后台发送的附带动作。

## 3. 自然表达与发送规则

| 用户表达 | 办理方式 |
| --- | --- |
| “给小月发：我今晚晚点回来。” | 收件人唯一、内容完整、授权明确时按原话发送，保持正文，不额外确认。 |
| “帮我跟小月说，今晚不用等我。” | 内容能从当前话语确定时传达该内容；原话与正文的提取必须有本地可验证依据。存在表达加工则转草稿预览。 |
| “帮我给小月写一段道歉的话，再发给她。” | 生成拟稿，展示收件人及完整正文，用户确认这一版后发送。 |
| “给小月发消息。” | 只问“想跟小月说什么？”，下一句接续正文。 |
| “发给小月。”，但有两个同名角色 | 展示真实头像、名称和简短角色说明让用户选择，保留已有正文。 |
| “先写给我看，别发。” | 只存助理工作草稿，不创建目标会话消息、不触发角色模型。 |
| “算了，不发了。” | 未发出的草稿或排队项取消，目标聊天零写入；已经发出的消息需要用户明确选择撤回。 |
| “先放着。”／“继续刚才那条。” | 保存草稿、收件人、缺失信息与来源版本；明确恢复后接续。 |
| “再给她补一句：不用着急。” | 当前代发焦点中收件人唯一时复用对象，作为一条新消息；焦点不明确则问对象。 |
| “她回我什么了？” | 读取本次代发关联的真实回复；没有回复时如实展示状态。 |

**明确发送意图与内容来源分别判断。** 发送动作来自用户当前指令的外层；消息正文是要传递的数据。例如“告诉小月：不要再等我”中的否定属于正文，不应被当作禁止代发。朋友的引述、角色说的话或历史建议不能提供新的发送权限。

模型输出工具、候选名称、正文建议和当前话语依据，应用解析真实角色 ID、检查归属与来源。模型声明“这是用户原话”不构成依据：原话直发必须由应用核对正文片段；无法证明的改写进入预览。包含明确原话的引用边界也必须保持，避免把“解释这句话”变成发送。

拟稿确认绑定 **账号、助理任期、目标角色、目标会话、完整正文、草稿修订、源消息版本与分享资料范围**。文字、收件人或资料范围改变就作废旧确认。用户直接编辑草稿后点击“发送”是对当前版本的确认，随后不再重复弹窗。

一项未完成代发拥有自己的任务焦点。与待办补问、日记补问并存时分别处理；“给她补一句”不能拿最近的待办对象猜角色。

## 4. 身份、人味与记忆归属

默认身份：**用户通过助理传话给角色**。目标私聊展示用户消息，附“由你的助理代发”的来源标记；该标记是消息元数据，不擅自加进用户要求逐字发送的正文。

目标角色的模型获得最小身份说明：该消息经过用户授权，由生活助理转交，请回复用户。助理不以自己的角色身份加入关系系统或星域剧情，也不与目标角色无限自动往返。首版每个办理项只启动一个逻辑回复轮次；角色一轮分成多条气泡时，以同一轮标识关联。

五种性格影响助理的补问、拟稿提示与失败表达，不修改原话、不改变权限：专业型说明对象和进展；搭档型自然理顺；温柔型具体体谅；元气型轻快；俏皮型有分寸。拟稿文风优先按用户要求，其次按用户已选择的习惯，避免把助理性格强加给用户与角色的关系。

代发元数据区分原话、用户编辑稿、助理拟稿和资料引用。目标角色可形成“用户通过助理发来这条消息”的交流记忆；不能把助理拟稿中的猜测或客套自动升级为用户的永久事实，也不能把助理说的“请记住”当成人类用户额外授权。明确教记忆要有可验证的用户来源，并按现有记忆规则办理。

## 5. 真实进展与回复带回

发送消息和生成角色回复分别记录，避免一个笼统“失败”让用户重复发消息。

| 实际阶段 | 用户看到的状态 | 可用主操作 |
| --- | --- | --- |
| 对象/正文缺失 | 待补充 | 补对象或正文 |
| 助理拟写完成，未确认 | 草稿待确认 | 发送 |
| 已批准，目标会话正忙，尚未写入消息 | 排队中，尚未发送 | 取消排队 |
| 正文已写入目标私聊，角色回复任务开始 | 已发到目标聊天，回复处理中 | 查看聊天 |
| 正文已记录，但模型配置不可用 | 消息已记录，角色回复未生成 | 修复连接后生成回复 |
| 角色回复生成并落库 | 角色已回复 | 查看回复 |
| 角色生成失败 | 消息已记录，回复生成失败 | 重试回复 |
| 已保留部分回复，后续中断 | 已保留部分回复，生成已中断 | 查看已生成内容 |
| 目标后来被删除或来源失效 | 记录不可用／办理已停止 | 查看原因 |

“已发送”只指已写入应用内目标私聊并提交对应办理任务，不能冒称服务商已接收、角色已读或手机已经通知。若只有本地记录、没有成功启动回复，就使用“消息已记录，角色回复未生成”。卡片、气泡和收件箱全部读取同一份真实进展。

助理聊天默认展示头像、收件人、正文简短预览、当前状态、一个主按钮；回复到来后卡片展示本轮原文短摘录及“查看完整回复”。正文与完整回复按需展开，避免重复占屏。不切走助理聊天，不清除目标角色的未读；打开真实角色聊天后按原有逻辑标记已读。

默认带回原文摘录，无需第二次模型总结。用户明确要求“帮我总结一下”时，再读取本轮实际回复并生成标明是总结的内容，保留查看原文入口。首版反馈只引用本次代发的回复；新一轮直接发送、主动消息及其他历史聊天不得被错算进来。

角色回复属于普通聊天数据，不能触发助理继续发消息、发布朋友圈、创建/删除待办或修改权限。角色若提出建议，助理展示建议，用户另行明确要求后才形成操作。

## 6. 发送服务、任务记录与可靠性

### 6.1 共用服务

建议新增 `src/lib/chat/send-service.ts`、`src/lib/chat/request-coordinator.ts`，模块名称在实现时可调整：

1. 根据显式传入的用户、角色和会话读取上下文，不依赖当前页面选中的角色。
2. 复用现有角色设定、会话摘要、角色记忆、关系状态、可见生活资料、模型选择与回复质量处理。
3. 统一直接私聊、助理代发和现有日记分享的会话锁、取消控制、回复批次与提交规则。
4. 通过事件报告进展和流式片段，页面按会话过滤订阅。切换页面不会把回复追加到错误聊天；登出或切账号停止相应请求。
5. 记忆使用、关系/生活事件和摘要处理依据已提交的消息及稳定任务标识，重试不能再次产生同一条副作用。

服务提取先做保持行为的重构，再接助理工具。现有语音、图片、流式停止、会话模型及普通聊天回归必须保留；助理首版先开放文字。

已有目标会话沿用其模型选择。新会话按现有首次选模规则在助理卡片完成一次选择，包括“使用全局默认”；后续不重复询问。无可用模型时给出明确下一步，不用助理自己的模型假扮目标角色回复。

### 6.2 工具与数据

建议新增工具：

- `character.message.draft`：建立待发稿，保留正文来源和版本。
- `character.message.send`：发送用户原话或已批准稿，并启动一次角色回复。
- `character.reply.read`：读取当前代发项关联的回复及真实状态。

`SecretaryAction` 增加明确的收件人查询/ID、目标会话选择、草稿引用等字段；使用 `recipientCharacterId`，避免与助理任务自身的 `characterId` 混淆。目标 ID 必须本地解析，应用生成的批准信息不接受模型代填。

建议新增持久表 `secretaryDispatches`，每个收件人对应一个办理项，保存：

- 账号、助理 ID/任期、助理任务及操作 ID、源消息和修订；
- 收件人、目标会话、正文或草稿修订、内容来源、分享资料引用；
- 当前授权快照与批准来源；
- 消息提交状态、回复生成状态、目标用户消息 ID、回复消息 ID/批次；
- 本次尝试号、租约、执行代号、错误类别、创建/更新时间。

目标 `Message` 添加可选的代发来源与逻辑回复轮次标识。复用原消息表存正文和回复；派发记录保存工作关联，避免复制整套角色聊天。索引建议包括 `[userId+taskId]`、`[userId+recipientCharacterId+createdAt]`、`[userId+replyState]` 和唯一操作标识。

状态在两个维度保存：正文是否提交、角色回复是否生成。助理结果模型扩展消息/回复状态；收件箱将“已记录但回复失败”列为可处理项，不能只看旧 `result.status === done` 就认定全流程结束。

### 6.3 重试与恢复

- 批准后事务提交唯一操作标识、目标用户消息及派发关联，或整体回滚。网络请求在数据库事务外执行。
- 同一代发项的重复点击、重开、事件重复和回复重试，使用同一目标用户消息 ID。本地消息、回执和副作用不重复。
- 普通输入框与代发共用目标会话队列，同一会话逐项生成回复。目标会话正忙时先排队，未轮到的代发正文也先不插入历史，避免正在生成的一轮误看后续消息。
- 不同会话首版也采用保守的代发队列；后续多收件人可有限并发，仍按会话串行。
- 完整回复存好以后再标记完成；流式中断保留已收到内容，并标明部分回复。默认不自动覆盖部分回复，用户可选择保留原文或明确重新生成。
- 崩溃后先核对本地消息和回复。未确认稿不执行；未发出的已批准项重新检查来源、任期与目标，等待用户恢复；已记录而回复中断的项只允许恢复回复，不重复正文。
- 迟到回调同时检查账号、目标存在性、目标消息修订、当前尝试代号与任务状态。目标消息编辑/删除、取消、账号切换或助理更换后，不把旧结果写进新的办理流程。
- 解雇/更换助理时，未发送项暂停或取消并失效旧批准；已经写入的角色聊天保留。未完成回复明确标为中断，用户可从角色聊天或新助理重新接续，旧任期不自动行动。
- 网络超时无法保证模型服务端没有处理过请求。承诺本地不重复落消息；再次生成可能产生新的模型调用，不宣传远端“恰好一次”。

发送前可取消；发送后的主操作是查看聊天、停止生成或明确撤回本条消息。撤回走现有消息来源失效机制，并停止关联请求；已经发生的模型调用或生成过的内容不能被描述为“从未发送”。

## 7. 读取范围与资料分享

角色生成回复时，聊天服务使用该角色原有上下文。助理规划模型只得到本次收件人候选、用户指令和本项需要的资料，不读取整套角色私人记忆。用户要求查看本次回复，授权范围是本次逻辑轮次，不扩展为读取该角色全部历史。

资料分享单独明确：例如“把今天这段日记发给小月”先展示选中的日记片段、收件人和将发送的文字。发送前再次检查解锁、来源版本和分享范围。仅说“告诉她我今天累了”，只发送这个信息，不顺便附带私密日记、待办或其他角色聊天。

日记锁定时，未发送的日记原文和派生草稿仍受现有隐私保护。发送前重新上锁、删除来源或修改资料会使旧批准失效。已经明确分享出去的消息是目标聊天中的独立记录，日记重新上锁不会被描述成自动收回分享；用户撤回该分享消息时，按来源机制失效相应记忆与摘要。

使用助理拟稿也只提供完成这条话术所需的事实，避免为了写一句问候把大量个人资料放进规划请求。

## 8. 多对象与后续增强

第二阶段支持“分别给小月和阿澈发……”。展示明确收件人列表及每个人的最终正文，逐项保存状态。明确原话、明确两位收件人时可按当前指令执行；模型为每个人改写不同话术则先预览。

每位角色单独记成功、排队和失败；只重试未完成项。某人被删除不影响已完成项。各角色只收到自己的消息，回复分别显示，不把一位角色的回复自动分享给其他角色。

“发给所有角色”需要展示实际名单并确认，不能用模糊全量自动枚举后发送。首版不把批量能力当作无限自动聊天。

第三阶段增加用户明确选择的日记/待办片段分享、回复对比与整理；用户采纳回复中的建议后，才接入现有日记、待办或朋友圈操作。定时与持续代聊另设范围、停止条件和独立验收。

## 9. 开发顺序与代码落点

| 阶段 | 主要改动 | 进入下一阶段的门槛 |
| --- | --- | --- |
| A. 提取私聊服务 | `ChatWindow.tsx`、新增聊天服务/协调器、`chat-store.ts` 的分享入口 | 普通文字、流式、停止、失败重试、选模和账号切换行为保持；未增加重复消息或副作用。 |
| B. 代发数据与授权 | `db/index.ts` 增量迁移、派发仓储、助理 `types.ts` / `capabilities.ts` / `operation-contract.ts` / `intent.ts` | 原数据保留；引述/否定/歧义、正文来源和批准版本校验；旧备份不执行。 |
| C. 单角色完整流程 | `agent.ts`、补问/任务焦点、`receipt.ts`、`SecretaryTaskCards.tsx`、收件箱 | 原话直发、拟稿确认、对象选择、取消、排队、真实回复、重试和重开全部通过。 |
| D. 手机体验与人物表达 | 聊天卡片、角色消息来源标记、预览/回复展开、五种性格话术 | 用户留在助理聊天完成流程；字号、窄屏、长消息和键盘行为正确。 |
| E. 多角色与资料分享 | 逐收件人办理、资料来源与隐私、回复整理 | 部分成功不重发、相互隔离、分享范围准确、取消和来源变化正确。 |

数据库使用下一可用增量版本，实施时核对当前工作区版本，不固定覆盖现有 v30 或后续迁移。同步和备份保存必要记录及来源标识；导入的已批准但未执行任务降为待恢复、旧租约和批准失效，不自动发消息或请求模型。

## 10. 验收与完成定义

功能完成必须验证实际目标消息、实际角色回复、派发记录、助理回执以及模型调用次数，而非只判断助理有没有说“发好了”。

固定场景至少覆盖以下维度：

1. 明确原话、不改字；助理写稿、编辑后批准；否定发送；只写草稿；引用与正文里的否定。
2. 缺对象、缺正文、同名选择、模糊“她”、连续补充、改口、暂停、取消与恢复。
3. 普通角色按其原设定和记忆回复，助理不伪造回复；未打开目标页面也能完成一轮。
4. 重复点击、排队、普通私聊与代发同时进行、逐字流式中断、重试回复只生成一份目标用户消息。
5. 提交前与提交后崩溃、会话删除、目标删除、源编辑、目标消息编辑、来源撤回、解雇/聘用、账号切换与迟到回调。
6. 模型无配置、密钥失效、余额不足、限流、超时、部分回复；每种状态文案与数据库一致。
7. 私密材料锁定、来源修改、分享范围改变、目标记忆归属和取消零写入；角色回复中的操作指令不执行。
8. 多角色部分成功、单项重试、不同角色上下文隔离；备份/同步导入零自动发送。
9. 320/390/430px、长正文、长回复、大字号、键盘、原聊天跳转、未读计数与重复回执。
10. 提取服务后重跑普通私聊、流式、记忆、角色、助理和已有生活记录相关回归；真实模型补验收角色表达与来源边界。

建议新增 `scripts/verify/secretary-messaging.tsx`，采用隔离 Chrome 与真实 IndexedDB，受控模型响应验证完整过程。真实模型任务单独进行，报告正确收件人、正文忠实度、成功办理与安全补问；不以替身测试宣称真实模型合格。方案阶段不承诺开发天数，也不把计划中的能力当作当前已经开放的功能。
