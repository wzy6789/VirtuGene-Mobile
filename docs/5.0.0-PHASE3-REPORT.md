## 1. 这一阶段让用户能做什么

世界页新增「**世界剧场**」：选一两个角色 → 写下一个地方（可写目标）→ 开一场戏。
之后：

- 你可以**让角色先开口**，或者**自己在这一场里做点什么、说点什么**；
- 每一次你的动作，会得到**一段戏**（旁白 + 多个角色的对白），像真的一起经历过一样；
- 演到合适的时候点「**结束这场戏并记下来**」→ 这场戏会**真的进入你们的世界**：
  年表里多一条「世界剧场」、可能留下一段**共同记忆**、**关系会变化并写清原因**、
  没说完的事变成**未完成的故事**；参与的角色**从此知道**这件事（没在场的角色一无所知）。
- 也可以「**先离开（不结算）**」：什么都不会发生，也不会花钱。

```
世界 → 世界剧场 → 开一场戏（0 次调用）
   → 每个用户动作：1 次调用 → 多条目正文（旁白/对白）+ 结构化状态
   → 先离开：0 次调用，无后果
   → 结束这场戏：1 次结算调用
        ↓ 建议 → **校验层**（VirtuGene 决定什么才算真相）
   stage 世界事件 · 共同记忆 · 关系变化（带原因）· 未完成事件（带 sourceSceneId）· 参与者认知
```

## 2. 成本纪律（§56/§57，本阶段最要紧的约束）

| 动作 | 调用次数 | 验收断言 |
|---|---|---|
| 打开剧场 / 打开一场戏 | **0** | F①、A① |
| 每个用户动作（含"让他们先开口"） | **1**（一次出多条） | B①、B⑧ |
| 先离开（暂停） | **0** | D① |
| 结束并结算 | **1** | C① |
| 已结束的场景再次结算 | **0** | C⑳ |

做法上**没有**出现"旁白一次 + 每角色一次 + 判定一次"的乘 3~5 倍设计：
一轮就是**一次请求**，返回 `entries[]`（旁白与对白混排），由我们的解析器逐条校验后落库。
整场戏的调用总数在验收里被逐次计数：**4 次推演 + 1 次结算 + 1 次 jsonMode 降级重试 = 6**。

## 3. "LLM 负责演，VirtuGene 负责记"具体是怎么做的

结算调用会返回一份**建议**（summary / 共同记忆 / 关系变化 / 未完成事件），但它进不了数据库——
必须先过 `src/lib/world/scene-consequences.ts` 的**校验层**：

| 建议 | 规则 | 处理 |
|---|---|---|
| `facets.affinity` | R7 已把该分面从世界层移除 | **丢弃并记名**（"未知分面:affinity"） |
| 分面增量离谱（如 +99） | 单次场景增量夹到 **±10**，总值仍夹 0~100 | 夹取 |
| 关系变化**没有原因** | 关系变化必须可解释 | **丢弃并记名** |
| 关系两端有**不在场的人** | 只能改"用户 + 本场参与者"之间的关系 | **丢弃并记名** |
| 未完成事件挂在**不在场**的角色上 | 只能挂在场角色 | **丢弃并记名** |
| 模型想指定"谁知道什么" | 认知由**参与者亲身经历**这一条我们的规则决定 | **忽略并记名**（"模型不得指定认知归属"） |
| 未知发言人（对白） | 绝不"随便安在某个角色头上" | **丢弃该条**并记名 |

被丢弃的内容会如实记录在 `dropped[]` 里（UI 不展示内部细节，验收与排查用），**绝不"猜一个"**。

## 8. 过程中的一个真实缺陷（测试抓到的）

**`finishSceneAndSettle` 原本没有"已经结束"的守卫**：对同一场已经结束的戏再点一次「结束」，
会**白花一次 LLM 调用**，并可能覆盖那次真实的结算结果（stage 事件是确定性 id 会被重写、
未完成事件理论上可能出现相似但不同的第二条）。

这是验收 C⑳ 直接抓出来的：第一次跑时 `calls: 1`（应为 0）。现在已修：
场景 `status === 'finished'` 时**直接返回"这场戏已经结束了"，不调用模型、不写任何东西**，
并在验收里长期盯住（0 次调用 + 如实报错）。

另外两处是我自己的断言写错（把"不在场"写成"场外"、把调用总数写成 7 而不是 6），已按实际语义改正。
